# ADR-0005：持久缓存、配额与下载完整性

- 状态：Accepted
- 日期：2026-07-16
- 补充日期：2026-07-27

## 背景

应用需要在无网络环境计算任意中国大陆发射点的 200 km 覆盖，同时所有底图、DEM、水体、计算结果、索引和临时文件共享不可配置的十进制 2.5 GB 上限。只按数据库记录求和会漏算 partial、损坏文件或遗留文件；静默淘汰又会让用户已准备的应急离线区域失效。

## 决策

1. 使用 `rusqlite 0.40.1` 和 bundled SQLite 保存区域、资产、版本、相对路径、期望/实际大小、SHA-256、ETag、状态和最后使用时间。
2. 缓存根由单进程独占文件锁保护。SQLite 使用 rollback journal、`synchronous=FULL`，不使用会留下额外 WAL 文件的默认方案。
3. 配额判断扫描缓存根的实际普通文件长度，拒绝符号链接。硬上限固定为 2,500,000,000 bytes，并为索引/事务保留最多 16 MB 余量；磁盘空间不足与配额不足分开报告。
4. 每个资产先写同目录 `<target>.partial`。服务器声明 Range 时从 partial 长度续传；否则安全截断重下。partial 的当前长度始终计入配额。
5. URL 只由内部 GLO-90 瓦片 ID 构造并限制为 `https://copernicus-dem-90m.s3.amazonaws.com/`。拒绝用户信息、查询、片段和相似域名。
6. 完成后验证 Content-Length 和可选的发布清单 SHA-256，`sync_all` 后同目录原子改名，再把 SQLite 状态置为 ready。无上游 SHA 时记录首次本地 SHA-256，之后使用前复核。
7. 区域与资产为多对多关系。删除区域只回收无其他引用的资产；活动区域拒绝删除；不实现自动 LRU 淘汰。
8. 每次计算只加载规划区域的 DEM 路径，不随缓存增长而解码所有瓦片。
9. 200 km 外接范围使用 WGS84 周界采样和一个 GLO-90 像素余量，不嵌入或推断政治边界。

## 结果

- 缓存无法通过未登记文件或 partial 绕过配额，代价是状态查询需要递归扫描数据根。
- 每次计算前重新读取全部 DEM 计算 SHA-256，成都 25 瓦片使加载阶段从约 1.6 秒增加到约 3.9 秒，但完整计算仍低于 60 秒目标。
- 本地 SHA-256只能发现首次下载后的变化，不能证明第一次收到的对象来自预期发布。签名清单仍是公开发行阻断项。
- 单进程锁简化了一致性；未来 Tauri 后端内部必须通过同一个 CacheService 串行化写操作。
- 删除完全由用户发起，符合应急离线数据的可预期性，但 UI 必须清楚显示配额不足和受影响区域。

## 2026-07-27 补充：重启整理与元数据边界

1. `CacheStore::open` 必须先执行文件/索引整理，再判断现有根目录是否超过硬上限。这样可先删除不应保留的陈旧或未登记 partial，但不会借整理名义删除仍与 downloading 状态、期望大小和强 ETag 一致的可信 partial。
2. 对 downloading 资产，若同目录原子改名已完成而 SQLite 尚未更新，则校验最终文件后推进为 ready；否则用真实 partial 长度修正索引。ready、missing、corrupt 资产旁的 partial 必须删除。
3. 整理完成后，根目录恰好等于 cap 可以打开；再多 1 byte 必须拒绝。该规则以真实普通文件扫描为准，不依赖 SQLite 的 `size_bytes`。
4. 会增长 SQLite 的区域/资产元数据写入必须先保留 headroom；批量区域和资产登记放在同一事务中，并在提交前复核根目录硬上限。失败时区域、资产和引用必须一起回滚。
5. 本补充由缩小配额的故障窗口测试覆盖，但不把它等同于真实 2.5 GB 实体缓存、磁盘耗尽或进程强制终止压力测试。
